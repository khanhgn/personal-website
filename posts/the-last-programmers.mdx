<p className="lede">The time between being wrong and finding out used to be a day. Then it was minutes, then seconds. Now it's zero. The agent is wrong, finds out, fixes it, and you never see any of it. Most of what I know about programming I learned inside that gap. This series is about what happens when it closes.</p>

I started university in 2023 and no longer write code by hand, so I'm close enough to the change to feel it. The question I care about is narrower than whether something is being lost. Something is always lost. Nobody misses punch cards. The question is whether what we're losing was load-bearing, and I think I can say which part was.

## I. The Price of a Mistake

Punch cards charged a day per mistake, so you ran the program in your head before the machine did. Agents charge nothing, and everything in between, terminals, view-source, Stack Overflow, was a shorter version of the same lesson: you learned whatever being wrong cost.

I started a year into the agent era but learned the Stack Overflow way, because ChatGPT still felt like cheating. There will be another era before I'm 25.

## II. It Feels Like Knowing

I got about a year of paying for my mistakes. First year, the computer science club's room, which we call the Duck Lounge, and a C++ game called Yippie Run that three of us built for our object-oriented programming class. A volcano erupts and Yippie runs from the lava across a level that never ends. We had a graphics library and nothing else. I did the gravity and the collision, and it took two overnights: things fell through the floor, then stuck to the ceiling, then fell through the floor again, and every one of those bugs was mine.

Then I started doing research, still in first year, and it was too hard to do alone, so I used ChatGPT. Then I used it for everything. A feature landed in minutes. A bug that would have cost me a day just disappeared, and I felt smarter than I'd ever felt, which should have been a hint. I had been programming for eleven months. Stopping to read the code felt like slowing down on purpose.

A lot of that feeling is borrowed. The model knew how to do it; I was there when it happened. I used to know what I understood and what I was taking on trust. Now there's a grey area of code I've skimmed, nodded at and shipped. Some of it I understand, and some I've only seen so often that it feels like I do. I can't tell which is which, because borrowed knowledge feels exactly like the real thing until the day you need it and the agent isn't there.

## III. Right for the Wrong Reasons

Philosophers have a name for believing something true for a reason that isn't what makes it true: a Gettier case, after a three-page paper from 1963 that they're still arguing about. The stopped clock that happens to show the right time. Code does this constantly. A function passes its tests and looks like code you've seen before, so you believe it's right, and it is, but not for those reasons. The real reason is somewhere nobody looked. Call it <Term id="gettier-code">Gettier code</Term>. James Somers [noticed](https://jsomers.net/blog/gettiers) it in debugging in 2019, before agents, and a paper this month, [From the Gettier Machine to Justified True Output](https://arxiv.org/abs/2610.38112), makes the same point about everything a model produces: fluent output makes you feel justified whether or not you are.

It is not a fancy name for buggy code, and the difference is the whole point. Buggy code is wrong. Gettier code is right, in production, today, and you don't know why. The first shows up in the tests, eventually. The second never does, because nothing is wrong. It turns into the first the moment something around it moves, and the person who moved it will have no idea what happened, because the reason it worked was never the reason anyone thought.

Programmers have always made some of it. Agents make it by construction. They write the code most likely to look right to a reader and a test suite, and looking right and being right overlap almost everywhere, which is why they're useful; the gap between the two is exactly where Gettier code lives. When they're wrong they find out and fix it before you see the failure, and the failure was the part that told you why the working version works, so you get the fix without the reason. And if the same agent writes the tests, the thing doing the work is also deciding what counts as working. I let mine do that for months. When a test failed, the agent fixed the code, or sometimes the test, and I didn't always check which. Part 2 is about that loop.

The usual reply is that compilers did this to us already and we were fine. A compiler is wrong rarely and in the same way for everyone, so a bug gets reproduced and fixed once. An agent is wrong in a new way each time, in your code, and the only person positioned to catch it is you.

Here is what it looks like. An agent writes a function that handles dates. The tests pass, it ships, and it works for a year. It works because every caller in the codebase happens to pass UTC, and the function quietly assumes that. Nobody wrote the assumption down, because nobody knew it was there, least of all the agent. Then someone adds a caller in Sydney. It's usually Sydney. The function was never wrong. Your reason for trusting it was, and the only person who could have found that out was the one who asked why it worked instead of whether.

## IV. Would I Have Noticed

So someone still has to read the code, and reading means something specific now. It doesn't mean looking at every line, which nobody can do at the rate agents write. It means asking one question of the parts you'll have to answer for: had this been false, would I have noticed?

If yes, because a test would have failed or the behaviour would have been visibly wrong, you have knowledge. If no, you have Gettier code, and the honest thing is to go and find the reason it works before you ship it. That's slower. I've stopped minding.

That someone is supposed to be me, and until a month ago, most days I wasn't doing it. I was doing something else, and it felt so much like work that I didn't notice.
