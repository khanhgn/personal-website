## I. The King's Complaint

<p className="lede">In the <em>Phaedrus</em>, Socrates tells a story about the invention of writing. A god offers it to the king of Egypt as a gift for memory, and the king is unimpressed. People will stop remembering, he says. They will seem to know many things while knowing almost nothing.</p>

Every generation makes some version of this complaint about the next, and it's usually wrong. Writing gave us law and science. But the king wasn't wrong. We did lose a kind of memory. We decided the trade was worth it, then forgot we'd made one.

So the question isn't whether something gets lost. Something always does. The question is whether it was load-bearing: whether anything important was resting on it.

I want to ask the king's question about programming: what are we losing, and was it load-bearing? I started university in 2023, learned the old way for about a year, then started leaning on ChatGPT. Now I don't write code by hand at all. That puts me close enough to the change to feel it. There are two easy answers. The first is that nothing is being lost: agents are just another layer, like compilers were, and we'll move up a level again. The second is that everything is: a generation that can't really program. I don't believe either one.

## II. Five Generations

Start with how people have learned to program so far. Each generation learned from whatever the machine charged them for. The price of a mistake kept falling, each drop came sooner than the last, and the lesson changed every time. There have been five generations.

**The first generation (1955–1975)** worked with punch cards. You wrote the program on paper, someone punched it onto cards, and you waited hours or a day for the result. A mistake cost you a day, so you ran the program in your head before the machine did. What they learned was precision.

**The second generation (1975–1993)** had terminals and then computers of their own. A run took seconds, so mistakes got cheap and people made them on purpose. Kernighan and Ritchie's book on C told you to run "hello, world" and then "experiment with leaving out parts of the program". What they learned was how machines fail.

**The third generation (1993–2008)** had the web, where every page came with its source. You learned by copying someone else's work and breaking it until you understood it, and mainstream languages started managing memory for you. What they learned was reading.

**The fourth generation (2008–2022)** had Stack Overflow, with an answer for almost everything. Copied code still rarely worked the first time, and making it work meant understanding it a little. What they learned was adaptation.

**The fifth generation (2022 onward)** started with the prompt and moved on to agents. Agents write, run and fix whole features, and catch most mistakes before you see them. What this generation learns is judgment: knowing whether what came back is right. The question is whether you can learn that without making the mistakes yourself. Part 3 is about the people that question is really for.

<FiveWays />

The time between being wrong and finding out went from a day, to minutes, to seconds. Now it's zero: the agent is wrong and finds out for you, and you never see it. Each step was shorter than the one before. That's what an exponential curve feels like when you're on it: it always seems to be speeding up right now.

Generations no longer line up with careers. The first generation learned and retired in roughly the same world. I started in the fifth generation's first year but learned the fourth's way, because using ChatGPT still felt like cheating. Now I work in the fifth. There will be a sixth before I'm 25.

## III. The Seam

Each generation passed something on to the next. A senior engineer looks at a diff and knows it's wrong before they can say why, because they wrote that exact wrong thing years ago and lost an afternoon to it. That's scar tissue. You can't write it down. You can only earn it.

I got about a year of it. I held out for a while. Then I used it, because everyone did and it worked. Now I describe problems to agents and judge what comes back. When the agent writes something I wouldn't have, I sometimes read it until I could have written it myself. That habit is the one thing from that year I want to keep, and for a long time I was losing it.

The reason was the euphoria. Working with agents felt amazing. A feature landed in minutes, a bug that would have cost me a day just disappeared, and I felt smarter than I'd ever felt. Stopping to read the code felt like slowing down on purpose.

But a lot of that feeling is borrowed. The model knew how to do it; I was just there when it happened. I used to know what I understood and what I was taking on trust. Now there's a big grey area: code I've read, nodded at and shipped. Some of it I understand. Some of it I've just seen so often that it feels like I do. I can't tell which is which, because borrowed knowledge feels exactly like the real thing until the day you need it and the agent isn't there. I'll come back to this feeling in Part 2.

## IV. Gettier Code

The usual answer is that this has happened before. Almost nobody reads assembly anymore, and compilers didn't make us worse engineers. We moved up a level.

It isn't the same. A compiler does the same thing every time and is almost always right, so you could stop reading what it produced. When it's wrong, it's wrong the same way for everyone, and someone fixes it once. An agent is wrong in a new way each time, in your code, and you're the only one there to catch it. Its output is plausible, not correct. Plausible just means it looks like correct code.

<Plausible n={2} />

Sometimes plausible code is wrong, like an answer to a coding puzzle that passes the example and fails the first hidden test. That's the easy case, because eventually you find out. The hard case is when it's right. Philosophers have a name for being right by luck: a Gettier case, where you believe something true for a reason that isn't what makes it true. In 2019, James Somers [wrote about](https://jsomers.net/blog/gettiers) how this shows up in debugging. Code can do the same thing. You think it's right because the tests pass and it looks like code you've seen before. It is right, but not for those reasons, and nobody knows the real ones. Call it <Term id="gettier-code">Gettier code</Term>. Nothing is wrong, so there's nothing to notice, until something around it changes and nobody can explain why it used to work.

So someone still has to read the code. That someone is supposed to be me, and until a month ago, most days I wasn't doing it. Part 2 is about what I did instead, and why it felt so much like work.
